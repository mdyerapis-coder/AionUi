# Desktop pet overlay — test plan

The desktop pet is two frameless, transparent, always-on-top windows. The draw window paints the SVG and ignores the mouse. A smaller hit window sits over the body and receives clicks. A main-process watchdog turns click-through back on if the hit window gets stuck. Dragging is the main process polling the cursor every 16 ms and moving both windows. A priority state machine plus an idle ticker picks the animation. Agent events are supposed to arrive through `setPetNotifyHook` in the main-process adapter (`bridge.emit` → the hook → `petEventBridge.ts`).

This plan says, for each behavior, whether this pull request automates it, automates the correct behavior as an expected failure, or leaves it for a person. Expected failures use Playwright `test.fail()` and name the bug. They are not skips. When the matching product fix lands, that test flips to "unexpectedly passed" and has to be unmarked.

Specs live in `tests/e2e/pet/` and follow the existing Electron fixture (`tests/e2e/fixtures.ts`, `AIONUI_E2E_TEST=1`). CI runs them with `xvfb-run` the same way as the other Electron specs. The suite is not part of the default pull-request workflow (e2e stays `workflow_dispatch`); the repeated xvfb runs recorded in the pull request are the evidence for this change.

## Show and hide

| Case                                                                     | Status                      | Why                                                                                                                                                                             |
| ------------------------------------------------------------------------ | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Settings "Enable Desktop Pet" creates the draw window and the hit window | Automated, expected pass    | Clicks the real settings switch, then reads `BrowserWindow.getAllWindows()` in the main process.                                                                                |
| Turning the switch off destroys both windows                             | Automated, expected pass    | Same path, the other direction.                                                                                                                                                 |
| Enabling twice does not open a second pair                               | Automated, expected pass    | `createPetWindow` is supposed to reuse the existing windows.                                                                                                                    |
| Right-click Hide hides both windows                                      | Automated, expected pass    | Invokes the real context-menu item (`pet.hide` → `hidePetWindow`).                                                                                                              |
| Tray Show/Hide brings a hidden pet back                                  | Automated, expected pass    | Invokes the real tray item. xvfb has no status-icon host and E2E mode destroys the tray icon, so the test calls the menu item's own click handler rather than clicking a pixel. |
| Tray Show/Hide hides a pet that is already visible                       | Automated, expected failure | Bug: the tray handler only calls `showPetWindow()`. After a right-click Hide, the tray is the only way back, and Show/Hide never hides.                                         |

## State changes during an agent run

Events are delivered with `bridge.emit` on the channels a real run uses today: `message.stream`, `message.userCreated`, and `turn.completed`. Specs do not call the state machine. After the channel fix, the same calls start driving the pet without a test change.

The bridge currently listens only on `chat.response.stream` and `openclaw.response.stream`. Tool-call and turn events are not mapped. `showConfirmation` is never called. Those are the expected failures below.

## Do-not-disturb freezes the animation

| Case                                   | Status           | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| -------------------------------------- | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Turning DND on returns the pet to idle | Expected failure | Setup clicks the body once (real `pet:click` → attention) and then ticks the real context-menu checkbox. The test checks that attention showed and that DND is actually on before it marks the failure. Bug: `setDnd(true)` clears timers and rejects new states, and it does not force idle, so the current animation stays on screen. The copy says "Pet stays idle, ignores AI events". Attention's auto-return is 3 seconds; the assertion waits 1 second, so a late auto-return cannot make this pass by accident. |

## Dragging and persistence

| Case                                                                       | Status                   | Why                                                                                                                                                                                                                                                                                                      |
| -------------------------------------------------------------------------- | ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A drag moves the draw window and the hit window by the same delta          | Automated, expected pass | xdotool moves the pointer. The test checks Electron sees that pointer, then calls `petHitAPI.dragStart` / `dragEnd` (the real preload IPC). Both windows must move together (about 12 px tolerance). If the cursor does not follow xdotool, the test fails loudly instead of asserting a stale position. |
| Size chosen in settings resizes the window and is written to ProcessConfig | Automated, expected pass | `system-settings:set-pet-size` writes `pet.size` and calls `resizePetWindow`.                                                                                                                                                                                                                            |
| DND chosen in settings is written to ProcessConfig                         | Automated, expected pass | Same for `pet.dnd`.                                                                                                                                                                                                                                                                                      |
| Settings page shows a size chosen from the tray                            | Expected failure         | The live window does resize. Bug: the tray click does not save `pet.size`, and the page reads the renderer settings cache, which the tray never updates.                                                                                                                                                 |
| Settings page shows DND chosen from the right-click menu                   | Expected failure         | The state machine does turn DND on. Bug: the checkbox does not save `pet.dnd`, so the settings switch stays off.                                                                                                                                                                                         |
| Size chosen in settings is restored after restart                          | Expected failure         | The value is on disk. Bug: startup reads `pet.enabled` and `pet.confirmEnabled` only, then creates the pet at the module default (280). The test waits until the window actually comes back, then expects width 360. A startup crash is a real failure, not an expected one.                             |
| DND chosen in settings is restored after restart                           | Expected failure         | Same startup gap. `setPetDndMode` is never called on launch.                                                                                                                                                                                                                                             |
| Dragged position is restored after restart                                 | Expected failure         | Bug: position is never written. Startup always places the pet at the bottom-right.                                                                                                                                                                                                                       |

Restart uses the same E2E user-data directory, so ProcessConfig survives. The suite quits the Electron process and launches it again.

`isPetSupported()` refuses only `--ozone-platform=headless`. Wayland is in scope. A passing Xvfb run does not prove the Wayland cases.

## Headless Wayland diagnostic (not CI)

sway 1.9 started with `WLR_BACKENDS=headless` and `WLR_LIBINPUT_NO_DEVICES=1`. It logged `drmGetDevices2 failed` and still created a `wayland-1` socket. The same specs were launched once with `--ozone-platform=wayland` and `--disable-gpu`, not under Xvfb. 25 tests matched their Xvfb outcome. Five did not:

- `setPosition` did not stick. `getPosition()` reported the hit window at `(0, 0)` instead of the 20% offset, and the draw window was 980 px away from the bottom-right of the reported work area (consistent with the window staying at the origin). Window size was correct (hit window 168 px, 60% of 280). Wayland does not give a client absolute placement the way X11 does; headless sway did not honor Electron's request. A real Hyprland or Plasma session can still differ.
- `getCursorScreenPoint` did not follow xdotool. The pointer stayed at `(1286, 703)` while xdotool asked for `(8, 8)` and `(40, 40)`. xdotool speaks X11, and this session had no X server (`xwayland disable`). Drag and the click-through watchdog could not be driven. The position-across-restart case failed in that setup, before its expected-failure assertion.
- Always-on-top: `isAlwaysOnTop()` was true for both windows. Nothing in the headless session showed whether the compositor actually stacked them above other windows.
- Transparency: still not inspectable. The same probes as on Xvfb (`transparent` / `frame` null, `getBackgroundColor()` not an alpha value the test can trust) and the flag test passed without learning anything new.

## What a person should still do on Arch

On a real Hyprland session and a real Plasma session, both native Wayland and (on Hyprland) XWayland:

- Enable the pet from Settings and confirm two windows, no frame, a see-through background, and clicks passing through the draw window onto whatever is behind it.
- Drag across a monitor boundary and restart. The pet should come back at the dragged size, DND, and position once those bugs are fixed. Until then, confirm the current behavior matches the expected failures above rather than something worse (pet missing, pet on the wrong screen, pet stuck modal).
- Right-click Hide, then use the tray icon (not the test hook) to show it again. Confirm the tray item still cannot hide a visible pet.
- Run a real agent turn and watch idle → thinking → working / tool call → confirmation bubble → done, and an error path. Today the pet stays idle; that is bug 1 and bug 2, not a compositor problem.
