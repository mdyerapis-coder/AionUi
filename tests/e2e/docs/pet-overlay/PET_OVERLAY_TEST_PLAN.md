# Desktop pet overlay — test plan

The desktop pet is two frameless, transparent, always-on-top windows. The draw window paints the SVG and ignores the mouse. A smaller hit window sits over the body and receives clicks. A main-process watchdog turns click-through back on if the hit window gets stuck. Dragging is the main process polling the cursor every 16 ms and moving both windows. A priority state machine plus an idle ticker picks the animation. Agent frames, including `confirmation.add`, travel on the backend WebSocket `/ws`. Only renderers subscribe. `setPetNotifyHook` / `bridge.adapter.emit` is a main-process path those frames never enter, so the pet receives nothing today.

This plan says, for each behavior, whether this pull request automates it, automates the correct behavior as an expected failure, or leaves it for a person. Expected failures use Playwright `test.fail()` and name the bug. They are not skips. When the matching product fix lands, that test flips to "unexpectedly passed" and has to be unmarked.

Specs live in `tests/e2e/pet/` and follow the existing Electron fixture (`tests/e2e/fixtures.ts`, `AIONUI_E2E_TEST=1`). CI runs them with `xvfb-run` the same way as the other Electron specs. The suite is not part of the default pull-request workflow (e2e stays `workflow_dispatch`); the repeated xvfb runs recorded in the pull request are the evidence for this change.

## State changes during an agent run

Dev Electron is launched with `tests/e2e/pet/backendWsProxy.mjs` as `AIONUI_BACKEND_BIN`. The proxy binds the port the app was given, forwards HTTP and `/ws` to the real aioncore, and broadcasts a posted frame to every connected `/ws` client (`POST /__e2e/ws-publish`). That is the socket the renderer already uses, and the socket a main-process pet client will use. aioncore does not rebroadcast a frame that a second client sends, and `bridge.emit` never sees these frames, so neither of those would keep failing after the pet subscribes.

Hermes, Claude Code, and Codex are ACP backends on `message.stream`. Frames use the real envelope (`name` or `event`, `data` or `payload`) and the real payloads (`thinking`, `text` / `content`, `acp_tool_call`, `tool_group`, `acp_permission`, `ask`, `finish`, `turn.completed`, `error`, `message.userCreated`). Specs do not call the state machine. Claude's AskUserQuestion is a `message.stream` frame whose type is `ask` (`session_id`, `request_id`, `questions[]`), not `acp_permission`. `acp_permission` data is untagged: a request (`tool_call` with optional `title`, `kind` `read` | `edit` | `execute`, and `raw_input`, plus `options[]` of `option_id` / `name` / `kind`) or a converted confirmation (`id`, `call_id`, `title`, `description`, `command_type`, `options[]` of `label` / `value`, and no `tool_call`). Upstream v2.2.2 no longer sends `confirmation.add`. The existing `confirmation.add` case stays; nothing new depends on that channel.

The pet main process does not open `/ws` today, so every assertion that expects the pet to leave idle is `test.fail()` with "pet does not subscribe to backend /ws yet". Assertions whose correct result is "stay idle" are real passes. They would go red if they were marked failing, and they still mean the right thing after the socket exists.

`live-stub-turn.e2e.ts` is the same subscription bug on a real backend turn. It registers `stubAcpAgent.mjs` through `POST /api/agents/custom` (no CLI agent and no model key). AionCore marks that agent online after `initialize` and `session/new`, then one `session/prompt` finishes with assistant text `stub-reply-ok`. Those two checks are real passes and run before `test.fail()`. The pet sequence (thinking, then working, then done, then idle or a sleep state) is the expected failure. Dozing at the start is the idle ticker, not required. Scripted `/ws` frames stay in `agent-events.e2e.ts`.

A few of those expected failures stay red after the socket lands. Some are the state machine (a new turn during `done`, a repeated `done` that does not refresh its timer, a late frame from a finished turn, and which conversation wins). Some are a smaller follow-up on top of that socket: a failed tool stays working, a cancelled team run or child turn returns to idle, a cron `error`, a disconnect during a running turn, and `cancelling` until a stopped turn goes idle. An `ask` frame mid-turn, an `acp_permission` request, and an `acp_permission` converted confirmation stay red until the pet maps those frames to needs-confirmation. The comments in `agent-events.e2e.ts` name which. Cron `skipped` / `missed`, a disconnect while idle, and team mailbox or task changes stay real passes.

## Headless Wayland diagnostic (not CI)

sway 1.9 started with `WLR_BACKENDS=headless` and `WLR_LIBINPUT_NO_DEVICES=1`. It logged `drmGetDevices2 failed` and still created a `wayland-1` socket. The same specs were launched once with `--ozone-platform=wayland` and `--disable-gpu`, not under Xvfb. 25 tests matched their Xvfb outcome. Five did not:

- `setPosition` did not stick. `getPosition()` reported the hit window at `(0, 0)` instead of the 20% offset, and the draw window was 980 px away from the bottom-right of the reported work area (consistent with the window staying at the origin). Window size was correct (hit window 168 px, 60% of 280). Wayland does not give a client absolute placement the way X11 does; headless sway did not honor Electron's request. A real Hyprland or Plasma session can still differ.
- `getCursorScreenPoint` did not follow xdotool. The pointer stayed at `(1286, 703)` while xdotool asked for `(8, 8)` and `(40, 40)`. xdotool speaks X11, and this session had no X server (`xwayland disable`). Drag and the click-through watchdog could not be driven. The position-across-restart case failed in that setup, before its expected-failure assertion.
- Always-on-top: `isAlwaysOnTop()` was true for both windows. Nothing in the headless session showed whether the compositor actually stacked them above other windows.
- Transparency: still not inspectable. The same probes as on Xvfb (`transparent` / `frame` null, `getBackgroundColor()` not an alpha value the test can trust) and the flag test passed without learning anything new.

## What a person should still do on Arch

On a real Hyprland session and a real Plasma session, both native Wayland and (on Hyprland) XWayland:

- Enable the pet from Settings and confirm two windows, no frame, a see-through background, and clicks passing through the draw window onto whatever is behind it.
- Drag across a monitor boundary and restart. The pet should come back at the dragged size, DND, and position once those bugs are fixed. Until then, confirm the current behavior matches the expected failures above rather than something worse (pet missing, pet on the wrong screen, pet stuck modal).
- Right-click Hide, then use the tray icon (not the test hook) to show it again. Confirm the tray item still cannot hide a visible pet.
- Run a real agent turn and watch idle → thinking → working / tool call → confirmation bubble → done, and an error path. Today the pet stays idle; that is bug 1 and bug 2, not a compositor problem.
